Atomid — architecture & code audit

An offline-first retail POS built in Flutter, with a hand-rolled Hive⇄Firestore sync engine. The data and domain layers are unusually well-reasoned; the gaps are concentrated in what happens after a cloud pull, and in a security surface that promises more than it delivers.

Section 01Executive Summary

Atomid is a single-tenant, offline-first point-of-sale and small-business ERP for one shop. It runs entirely on-device against Hive, and treats the cloud as an optional mirror rather than a source of truth. That decision is applied with real discipline: every screen works signed out, and the sync engine is a queue with backoff and a dead-letter state rather than a naive write-through.

The strongest part of this codebase is its data and domain layer. StorageRepository is large but coherent, and the reasoning behind non-obvious decisions is written down in comments that explain the failure that motivated them — carried-forward ledger balances, device-tagged invoice numbers, paged Firestore reads that replaced a silent limit(500) truncation. This is materially better than typical application code, and it is the main reason the project is workable at its current size.

The weaknesses cluster in three places:

  1. Post-pull state is incomplete. applyRemote writes records into their boxes but never updates the in-memory indexes the till reads from. After a cloud pull — including the very first one on a newly provisioned device — customer phone lookup returns nothing and visit history reads as zero. This is confirmed empirically, not inferred.
  2. The security surface overstates itself. A "Enable Biometric Login" toggle is persisted, synced and preserved across restores, but local_auth is never called anywhere in the codebase. There is no app lock of any kind. The README additionally advertises RBAC that was deliberately removed from the code.
  3. Sync is full-refresh only. The incremental-pull code path exists, is correct, and is never reachable — no caller ever passes since. Every sign-in and every manual refresh re-downloads every collection in full.

None of these are architectural dead ends. The first is a handful of missed index-rebuild calls; the second is a product decision that needs to be made honestly; the third is a one-line plumbing change plus a stored watermark. The architecture underneath them is sound and worth preserving.

Bottom line

Ship-worthy foundations with three specific defects that should be closed before this is relied on across more than one device. The codebase does not need a rewrite, or even a significant restructure — it needs the post-pull path finished and the security story made truthful.

Section 03Project Overview

What it is: a cross-platform retail management and point-of-sale application for a single small shop — one account, one business, potentially several devices.

The problem it solves (strongly inferred from code and the pubspec description "Offline-first retail and point-of-sale for small shops"): a shop till must keep working when the internet does not. Most POS products fail closed when connectivity drops. Atomid inverts that: the local Hive database is the system of record, and Firestore is a replica that catches up later.

Likely users: the owner-operator of a single retail outlet (clothing/apparel is strongly implied — products carry size, color, brand variants, and the OCR tag reader parses S/M/L/XL/XXL). Currency defaults to ₹ and GST fields appear throughout, so the target market is India.

Architectural principles the code actually follows

  • Local first, always. No screen requires network or sign-in. bootstrap() treats Firebase failure as non-fatal (bootstrap.dart:66-78).
  • One construction path. Providers throw UnimplementedError unless injected from bootstrap(), so tests and the app share one object graph (app_providers.dart:41-63).
  • Explain the failure, not the code. Comments consistently document what broke to motivate a design, e.g. firebase_repository.dart:157-169.
  • Compensate, don't pretend to transact. Hive has no cross-box transaction, so multi-step operations register undo steps.

The two mechanisms worth understanding first

1. Topic-based invalidation

Every mutation funnels through StorageRepository.enqueueSync(), which does two jobs: it queues the cloud write and emits the affected DataTopics on a broadcast stream (storage_repository.dart:506-511). DataVersionNotifier listens and bumps a per-topic counter; read providers call _watch(ref, topic) to subscribe to just their slice.

This is a good design. It removes the classic bug where a screen forgets to invalidate after a write — the comment at app_providers.dart:66-70 says exactly that was the previous arrangement. The mapping lives in one switch (_topicsFor, storage_repository.dart:545-573), so a sale correctly invalidates sales, inventory and products.

2. Compensating transactions

Hive cannot transact across boxes. A checkout touches five. SaleService.checkout() therefore builds a list of undo closures as it goes and replays them in reverse on failure (sale_service.dart:113-152, _unwind at :305-313). A durable journal backs this up for process-death (see §13). PurchaseService._receive() uses the same pattern.

Notably absent

  • No router. Navigation is an IndexedStack index plus Navigator.push(MaterialPageRoute(...)). No deep links, no URL routing on web.
  • No background workers or scheduled jobs. Sync is a Timer.periodic every 2 minutes plus event triggers, all in-process (sync_service.dart:162).
  • No caching layer beyond in-memory indexes and one derived-totals cache.
  • No structured logging or telemetry. debugPrint throughout; a SyncLogModel box is the only persistent diagnostic trail.

Section 07Module-by-Module Analysis

7.1 StorageRepository — the hub

Filelib/data/repositories/storage_repository.dart — 2,676 lines
Depends onAll 18 models, EntityCodec, Ids, Fmt, AppException, PlatformIo, Hive
Depended on byEvery domain service, every read provider — the single most connected file in the project

Responsibilities: box lifecycle and crash recovery; CRUD for every entity; three in-memory indexes; the sync queue; the wire-format encode side (getEntityJson); conflict resolution (applyRemote); backup snapshot export/import; document numbering; ledger balance arithmetic; loyalty point recomputation; inventory valuation; the checkout journal.

Assessment. This is a God object by size, and it is substantially better than that label usually implies. The internal organisation is disciplined — clearly banded sections, a consistent enqueue-then-notify pattern, and genuinely excellent comments. Splitting it would be a large, risky refactor for modest gain; see §21 on what not to touch.

Its real weakness is not size but a split-brain between stored state and derived state. Three in-memory structures — _barcodeIndex, _mobileIndex/_indexedMobile, _salesByCustomer, plus _customerBalances/_supplierBalances and the _todayCache/_costPriceIndex caches — must be kept in step with the boxes by hand. Local writes do this correctly. Remote writes do not (§22, finding B-1).

7.2 SaleService — checkout

lib/domain/services/sale_service.dart (337 L). Owns the checkout transaction. Validates stock (summing per-variant so a duplicated line can't oversell), enforces credit limits, prices via SalePricing, then writes sale → stock-out per line → ledger → loyalty → lifetime spend, registering an undo for each. Opens a durable journal before the first write and closes it after the last.

Edge cases handled: empty cart; product or variant deleted since it entered the basket; insufficient stock; credit sale without a customer; credit limit breach; walk-in (no customer) skipping all ledger/loyalty work; discount capped so it can't push a part-redeemed bill negative.

Assessment: the best-designed service in the project. Clear single responsibility, explicit failure semantics, well tested (sale_service_test.dart, sale_rollback_test.dart, checkout_crash_recovery_test.dart).

7.3 SyncService — replication

lib/domain/services/sync_service.dart (480 L). Upload is queue-driven in batches of 20 with exponential backoff (2^retryCount × 30s, :321-326) and a dead state after 5 retries. Download is a full pull on sign-in and on demand. Emits a SyncStatus the UI subscribes to.

Assessment: genuinely good scheduling logic, and the SyncWrite abstraction (firebase_repository.dart:12-29) keeps Firestore types out of the engine so batching decisions are testable without a live project — fake_firebase_repository.dart subclasses the real repository so a leak of Firestore types breaks compilation. Two defects: the incremental path is unreachable (§21), and a pull leaves derived state stale (§22).

7.4 PurchaseService — receiving

lib/domain/services/purchase_service.dart (207 L). Status machine Draft → Issued → Received, with Cancelled as a side exit. Receiving is the only transition with side effects: stock-in per line plus a supplier ledger credit. Validates every line up front, holds the status back until receiving fully succeeds, and unwinds on failure.

Assumption worth knowing: previousStatus must be passed by the caller, because Hive returns the same instance the caller mutated — re-reading cannot detect the transition. This is documented at :31-34 and is a real trap for anyone adding a call site.

7.5 CustomerService, SupplierService, ExpenseService

Thin. CustomerService (131 L) adds phone normalisation, registration-by-mobile, duplicate detection and merge. SupplierService (61 L) and ExpenseService (63 L) are near-pass-throughs to the repository that mostly add an ActionHistory write — arguably not earning their existence, though they do give the UI a stable seam.

7.6 AuthService / SessionService

AuthService (59 L) wraps Firebase Auth and guards every call with _requireAvailable(). Its class comment is the clearest statement of the security model in the project: "Signing in is not a permission boundary — every screen works without it."

SessionService (100 L) persists a per-install device id used to tag offline document numbers so two devices cannot both issue invoice 0001. It has its own untyped Hive box with independent recovery logic — a small duplication of _safeOpenBox.

7.7 BackupService

(220 L) Point-in-time JSON snapshots, distinct from sync — the class comment articulates why: "Cloud sync is a live mirror, not a backup: it faithfully replicates a mistake." Writes to a staging file then renames, so a crash leaves the previous backup intact. Keeps 10, prunes the rest, never fails the operation over pruning. Android writes to external storage specifically because app-private storage dies with an uninstall.

7.8 ExportService

(1,306 L, lib/core/services/) Pure static PDF generation: invoice, thermal receipt (80mm roll), sales/inventory/purchase/supplier/valuation reports, single and bulk price tags. Caches fonts, themes and the logo in statics.

Assessment: the weakest-structured large file. Entirely static with mutable static caches (_cachedThemes, _resourcesLoaded), which makes it untestable in isolation and gives it process-lifetime state. It is also the only major module with no test coverage.

10.4 Upload

Triggers: connectivity regained, auth state change, 2-minute timer, or manual. processQueue is reentrancy-guarded by _isSyncing. Per batch of 20 it skips items over the retry ceiling or inside their backoff window, marks the rest SYNCING, builds SyncWrites, commits atomically, then on success deletes the queue item and on failure increments retryCount. Every outcome writes a SyncLogModel — this is what the System Console reads.

Section 11Frontend & UI Analysis

Structure

AppShell (presentation/widgets/app_shell.dart, 312 L) is the only persistent chrome. It renders three layouts from one ResponsiveBuilder: NavigationBar + "More" sheet on mobile, collapsed NavigationRail on tablet, extended rail on desktop (:193-199).

Screens live in an IndexedStack, but only ones actually visited are constructed — :182-191. The comment explains why: handing it all eight destinations meant the first frame after startup built every list, dashboard and report before the user had looked at any of them. Section 13Sync Engine — detailed

Wire format

Encode lives in StorageRepository.getEntityJson(); decode lives in EntityCodec. They are two hand-written mirrors of one format, which is a real hazard — a field added to one and not the other vanishes silently. The codec's own comment names two historical instances (Expense.title, Purchase.status). test/unit/sync_payload_test.dart now guards the round trip. Mitigated

Conflict resolution

applyRemote(type, id, json):
  1. if any sync_queue item exists for (type,id) and status != DEAD  → REJECT remote
  2. remoteUpdatedAt = json.updatedAt ?? updatedDate ?? createdDate
     localUpdatedAt  = _localUpdatedAt(type, id)
     if both non-null and !remote.isAfter(local)                     → REJECT remote
  3. otherwise decode and put

Rule 1 is the important one: unsent local work always beats the cloud, so a pull can never destroy something this device hasn't uploaded. That is the right priority for offline-first.

LWW guard is inactive for 8 of 15 syncable types

MediumConfirmed

storage_repository.dart:1261-1280 — _localUpdatedAt

_localUpdatedAt returns a timestamp only for Product, Customer, Supplier, Sale, Purchase, LoyaltyTransaction and Expense. For CustomerLedger, SupplierLedger, InventoryMovement, ExpenseCategory and the four config singletons it returns null, so step 2 is skipped entirely and any remote copy overwrites local unconditionally (once step 1 passes).

For immutable-by-nature records (movements, ledger rows) this is mostly harmless — they are append-only, so an overwrite writes the same values. For config singletons it is a genuine last-pull-wins: settings, company profile, invoice settings and loyalty rules are all mutable and all unprotected by recency. Two devices editing tax rate will see the most recently pulled value win rather than the most recently edited one.

Paging

fetchCollectionPages pages at 300 by FieldPath.documentId, applying each page as it arrives so peak memory is one page. Its comment records that this replaced a single limit(500) with no orderBy — which silently truncated any shop with more than 500 products and returned a non-deterministic subset. That fix is a good catch and well documented.

Backoff and dead-lettering

2^retryCount × 30s, ceiling of 5 retries, then DEAD. Dead items are excluded from normal processing, counted in SyncStatus.dead, surfaced in the System Console, and re-queueable via retryFailed(). Permission-denied is detected by string matching (:454-456) — fragile, but it only drives a message, not control flow.

Crash-safety of checkout (the durable journal)

Added this session. Before the first write, a row is written to checkout_journal and flushed; it is removed on success or after an in-memory unwind. Anything left at startup is a checkout the process didn't survive, and recoverInterruptedCheckouts() reverses it.

The design choice worth preserving: the journal stores almost nothing — sale id, invoice number, customer id, and the customer's pre-sale lifetimeSpend. Recovery finds everything else by querying what references the sale (movements by movementReferenceId, ledger rows by referenceId, loyalty rows by saleId). A step-by-step log would be wrong precisely when the crash falls between doing a step and recording it; reference-driven recovery is accurate wherever the crash landed, and idempotent because each movement is deleted as it is reversed.

Residual exposure: a crash between the two writes inside a single performStockOut (product save, then movement record) — microseconds, versus the whole multi-write checkout previously. Closing it entirely would need a WAL inside Hive.

Section 14Authentication & Authorization

The model, stated plainly

There is one account and no authorization model at all. This is deliberate and documented in three places: auth_service.dart:7-11, session_service.dart:11-16, and the comment block in firestore.rules. A previous store-and-membership design with roles was removed.

  • Authentication: Firebase email/password only. No OAuth, no MFA, no email verification enforcement.
  • Authorization (cloud): one rule — request.auth.uid == userId on /users/{userId}/{document=**}, with a catch-all deny. This is correct, minimal and easy to verify.
  • Authorization (app): none. Signing in gates cloud sync only. Every screen, every record, every export works signed out.

S-1 · "Enable Biometric Login" is a switch wired to nothing

Section 16Performance Review

Confirmed issues

P-1 · Every pull re-downloads every collection in full

HighConfirmed

sync_service.dart:158, 377 · sync_status_widget.dart:185 · system_console_screen.dart:166

pullAll({DateTime? since}) supports incremental sync, and fetchCollectionPages implements the since branch correctly. No caller ever passes it — all three call sites use pullAll(). Every sign-in and every manual refresh therefore fetches all 15 collections in their entirety, 300 documents per round trip.

For a shop with two years of sales this is thousands of reads per sign-in, with direct Firestore cost and a long "Fetching your data…" state. Fix: persist a lastPulledAt watermark and pass it. Note the since branch orders by updatedAt, which is written as an ISO-8601 string — lexicographic ordering matches chronological for that format, so the comparison is valid, but any record written before updatedAt existed would be skipped, which is exactly why the full path exists as the fallback.

MediumConfirmed

storage_repository.dart — getAllSales, getPurchases, getSuppliers, getAllMovements, getHistory

storage_repository.dart:1261-1280

See §13. _localUpdatedAt returns null for settings, company, invoice and loyalty config, so the recency comparison is skipped and remote always wins. Two devices editing tax rate or loyalty rules can silently clobber each other. Config models carry no updatedAt field at all, so fixing this needs a model change plus adapter regeneration.

B-3 · Report date-range boundaries include up to a day of extra data

MediumConfirmed

storage_repository.dart:2069-2075 (getSalesByDateRange) · reports_dashboard_screen.dart:36-40

getSalesByDateRange tests isAfter(start − 1 day) && isBefore(end + 1 day), which pulls in sales from the day before start and the day after end. Separately, the "This Week" filter computes now.subtract(Duration(days: now.weekday − 1)) — retaining the current time of day rather than snapping to midnight — then subtracts another full day. A "this week" revenue figure can therefore include part of the previous Sunday.

These are reporting figures a shop owner may reconcile against cash. Normalise both ends to midnight and use inclusive comparisons.

B-4 · Multi-device credit limit race

MediumConfirmed

sale_service.dart:192-211

_assertCreditAllowed checks against the local copy of currentBalance. Two tills selling to the same credit customer before either syncs can each pass independently and jointly exceed the limit. Accepted by the owner for now — the deployment is a single shop. Revisit if a second till is added; the fix is credit reservation or post-hoc flagging, not a tighter check.

B-5 · Loyalty balance silently clamps at zero

LowConfirmed

storage_repository.dart:2591-2601 (_recomputeRewardPoints)

If summed transactions go negative the total is set to 0 with no record of the discrepancy. The comment acknowledges the choice ("not throwing here allows corrections"), but a customer whose points went negative through a data issue loses the evidence. Consider logging an ActionHistory entry when the clamp fires.

B-6 · Action history is device-local and never synced

LowConfirmed

storage_repository.dart — history box absent from syncableEntities

The audit trail — including the "interrupted sale reversed" notices written by crash recovery — exists only on the device that produced it, and is capped at 2,000 entries. Arguably intentional (the code calls it "a convenience log, not a ledger"), but it means the record of an automatic sale reversal can be lost, and is invisible from any other device.

B-7 · ActionHistory id reuses the movement id

LowConfirmed

storage_repository.dart:1518-1526 and the stock-out equivalent

Stock in/out write history with id: movement.id. No collision today (movement ids are fresh v4 UUIDs), but it couples two record spaces for no benefit and would break if a movement ever wrote two history entries.

Section 23Architecture Problems

A-1 · Derived state is maintained by hand, in two places, with no shared discipline

This is the root cause behind B-1 and the highest-leverage structural issue in the codebase. Every write path must remember to update up to six in-memory structures, and there are two families of write path — local (saveX) and remote (applyRemote) — which have diverged. Local paths are correct; remote paths are partially correct.

Recommendation: make index maintenance a single function keyed by entity type, called by both families. Something like _reindex(entityType, id) invoked at the end of both saveX and applyRemote. This converts "remember six things at every call site" into "one call, one place" and structurally prevents the class of bug rather than fixing one instance.

A-2 · The wire format is hand-mirrored

Encode and decode are separate hand-written functions in separate files that must agree field for field. The round-trip test is a good mitigation but it is a smoke alarm, not a sprinkler — it catches the omission after someone makes it. Longer term, generating both from the model annotations (or hand-writing one and deriving the other) removes the class entirely. High effort; not urgent.

A-3 · Domain depends on presentation for one type

sale_service.dart:11 imports CartItem from presentation/providers/cart_notifier.dart. Move CartItem into domain/ (it is a pure value type — product, variant, quantity, computed total). Low effort, restores the layering.

A-4 · No abstraction boundary around Hive

Models extend HiveObject and Box<T> is used directly throughout the repository. This is a deliberate-looking trade — it keeps the code simple and Hive is the system of record, so the coupling is to the thing that matters least to change. Noted rather than criticised, but it does mean the repository cannot be unit-tested without a real Hive directory (which TestStore handles well).

A-5 · One user is assumed everywhere, and that assumption is now load-bearing

Roles, memberships and store scoping were removed. The Firestore rule, SessionService, and AppShell._visibleDestinations() all encode "one user" directly. This is fine and simplifying today, but it is worth being conscious that reintroducing staff accounts would touch the rules, the sync path scoping, the session model and the navigation — it is not a feature that can be bolted on.

Section 24Strengths — what should NOT be changed

The comment culture

Preserve

Comments explain the failure that motivated the design. This is rare and extremely valuable. Any refactor that strips these comments makes the codebase materially worse even if the code gets shorter. Treat them as source.

The compensating-transaction pattern in SaleService and PurchaseService

Preserve

Correct response to Hive's lack of cross-box transactions, applied consistently, and now backed by a durable journal for process death. Don't replace this with something clever; extend the same pattern to any new multi-step operation.

Topic-based invalidation

Preserve

Removes a whole class of stale-UI bug by making invalidation a property of the write rather than a responsibility of the reader. The single _topicsFor mapping is the right shape.

TestStore and FakeFirebaseRepository

Preserve

Testing against a real repository on a temp directory, and a fake that subclasses the real cloud repository so type leaks break the build, is a better testing strategy than heavy mocking would give. Keep new tests on this foundation.

SyncWrite as a boundary type

Preserve

Keeping Firestore types out of the sync engine makes every scheduling decision testable offline. Resist any shortcut that reaches for WriteBatch directly.

Defensive decoding in EntityCodec

Preserve

Every field is type-checked with a fallback, so a malformed or partial cloud document degrades gracefully instead of throwing mid-pull. This is what lets a schema evolve without breaking older clients.

_safeOpenBox's graduated recovery

Preserve

Retry → crash recovery → rebuild, with the loss recorded in recoveredBoxes and shown to the user. Data loss is never silent. Do not simplify this into a single try/catch.

Where refactoring would create more risk than value

  • Splitting StorageRepository. It is large but coherent, heavily depended upon, and well tested through TestStore. A split would touch every service and provider for organisational benefit only. Fix A-1 inside it instead.
  • Replacing Hive. The coupling is deep and the current behaviour (including compaction tuning and crash recovery) is tuned. No evidence this is a problem.
  • Rewriting the sync engine. The scheduling, backoff, dead-lettering and paging are all sound. It needs two fixes (B-1, P-1), not a redesign.

Section 30Final Assessment

Atomid is a well-built application with a clear thesis, executed with unusual discipline in its data and domain layers, and let down in three specific and fixable places.

The offline-first commitment is real, not marketing. The app genuinely works with no network and no account, and the code repeatedly chooses the harder correct path — compensating transactions instead of hoping writes succeed, graduated box recovery instead of deleting on first error, paged cloud reads instead of a convenient limit(), backups deliberately separated from sync because a mirror replicates mistakes. Several of these read as lessons learned the hard way and then written down, which is the best possible state for a codebase to be in.

What holds it back is not architecture but completeness at the seams. The remote write path was built after the local one and never quite caught up: it updates storage but not the derived state the till reads from, and the result is a confirmed defect that breaks customer lookup at exactly the moment a new device is provisioned. The security surface has the opposite problem — a control exists in the UI with no implementation behind it, which is worse than having no control at all. And a well-written incremental sync path sits unreachable behind a parameter nobody passes.

None of that requires a rewrite. The critical fix is roughly a one-line change plus a regression test. The second is a product decision followed by either a deletion or a half-day of work. The third is a stored timestamp.

If you do only three things
  1. Rebuild the customer indexes after a pull (R-1) — this is actively wrong today, silently, on new devices.
  2. Make the biometric toggle honest (R-2) — implement it or remove it, but do not ship a security control that does nothing.
  3. Fix the README (R-4) — it currently promises a permission model the code deliberately removed.

What I understand about this project — in plain language

Atomid is a cash register and back-office for one small shop, most likely a clothing store in India. It runs on a PC or phone in the shop, and the important design decision is that it does not need the internet. Everything — every sale, every stock change, every customer — is written to a database on the device itself. That local copy is the real one.

If the shop has an internet connection and the owner signs in, the app also keeps a copy in the cloud, so a second device or a replacement PC can pick up where the last one left off. But the cloud copy is a mirror, not the master. If the connection dies mid-day, nothing stops; changes pile up in a queue and go up later, retrying with increasing patience and eventually giving up loudly rather than silently.

The shop owner can: ring up sales by scanning barcodes, apply discounts and loyalty points, print an A4 invoice or a thermal receipt; track stock with a full history of every movement; keep customer records with phone lookup, purchase history, credit limits and running balances; raise purchase orders to suppliers and receive them into stock; record expenses; print barcode price tags; and take local backups.

The code is organised in three layers — storage, business rules, screens — and that separation is respected. The trickiest part is that the local database can't do "all of these changes together or none of them", which matters because a single sale changes five different things at once. The developers solved this by recording how to undo each step as they go, and by writing a small note to disk before starting so that if the power is cut mid-sale, the app finds the note on restart and reverses the half-finished sale rather than leaving the books wrong.

Three things are currently wrong. First and most serious: when the app downloads data from the cloud, it puts the records away correctly but forgets to rebuild its quick-lookup shortcuts — so on a freshly set-up second device, typing a customer's phone number finds nothing, even though the customer is right there in the database. It fixes itself when the app is next restarted, which is why it hasn't been noticed. Second: the Settings screen has a "Enable Biometric Login" switch that saves its setting and syncs it to the cloud, but nothing in the app ever checks it — there is no fingerprint lock, and in fact no lock of any kind. Third: every time it syncs, it re-downloads everything rather than just what changed, which will get slow and expensive as the shop's history grows.

Everything else is in good shape, and the comments left in the code explaining why things are the way they are make it a genuinely pleasant codebase to pick up.
