Deep Audit Findings

1. Multi-Terminal Inventory Overselling

Severity: 🔴 Critical | Category: Inventory / Synchronization

Evidence: storage_repository.dart (lines 2280-2284), sync_service.dart (line 241)

Current Behavior: When an offline sale occurs, the system calculates the absolute new stock quantity locally (e.g. variant.quantity -= quantity) and enqueues the entire Product entity to be synced. When it syncs, Firebase overwrites the cloud document using Last-Write-Wins (LWW).

Impact: If Terminal A and Terminal B both process sales for the same product while offline, the terminal that syncs last will overwrite the other's stock deduction, artificially inflating inventory and hiding sales data.

2. Local Database Unencrypted

Severity: 🟠 High | Category: Security

Current Behavior: Hive CE database initialization does not utilize HiveAesCipher. All business data, including customer PII, ledger balances, and lifetime spend are stored in plaintext on the device filesystem.

Impact: A stolen or compromised device gives the attacker complete access to the store's entire operational data footprint.

3. Missing Dead-Letter Alerting

Severity: 🟡 Medium | Category: Reliability

Current Behavior: When queue items reach 5 retries, they are marked as DEAD. While the UI likely surfaces this status, there is no automatic central reporting. Store managers will only know data is missing if they physically check the terminal.

4. Robust Invoice Number Isolation (Confirmed Safe)

Severity: 🟢 Success | Category: Data Integrity

Evidence: storage_repository.dart (line 2467)

Behavior: The system embeds a unique _deviceTag into the offline invoice sequence (INV-DATE-TAG-0001). This natively and securely prevents invoice number collisions across offline terminals without requiring central coordination.

5. Excellent Transaction Idempotency (Confirmed Safe)

Severity: 🟢 Success | Category: Synchronization

Behavior: Duplicate offline sales uploads are completely prevented. The system creates UUIDs locally for transactions before queueing them. Uploads utilize Firestore set(..., merge:true). Even if a network disconnects during the upload ACK, a retry simply overwrites the exact same data safely.
